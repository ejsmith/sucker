# Sucker! Multiplayer Setup

This app is moving to a server-authoritative async multiplayer model.

## Backend

Use Supabase for:

- Auth and profiles
- Postgres game storage
- Row Level Security
- Realtime game updates
- Edge Functions for trusted game mutations
- Push token storage

The server-authoritative game actions live in Supabase Edge Functions. That keeps
the service role key out of the app and keeps dice rolls, scoring, token spends,
and stat writes off the client.

Apply the schema:

```sh
supabase link --project-ref <project-ref>
supabase db push
```

Deploy the game action function:

```sh
supabase functions deploy game-action
```

Required Supabase Edge Function secrets:

```sh
supabase secrets set SUPABASE_URL=https://<project-ref>.supabase.co
supabase secrets set SUPABASE_ANON_KEY=<anon-key>
supabase secrets set SUPABASE_SERVICE_ROLE_KEY=<service-role-key>
supabase secrets set WEB_PUSH_VAPID_PUBLIC_KEY=<vapid-public-key>
supabase secrets set WEB_PUSH_VAPID_PRIVATE_KEY=<vapid-private-key>
supabase secrets set WEB_PUSH_VAPID_SUBJECT=mailto:notifications@sucker.games
```

Never put the service role key in the mobile app.

For Apple login and linking Apple to existing player accounts, follow
[Sign in with Apple setup](apple-sign-in.md).

The `game-action` function also sends Expo push notifications directly through
Expo's push API after successful server-authoritative game actions. It also
sends standards-based Web Push notifications to PWA installs when VAPID secrets
are configured.

## App Environment

Copy `.env.example` to `.env.local`:

```sh
EXPO_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
EXPO_PUBLIC_SUPABASE_ANON_KEY=your-anon-key
EXPO_PUBLIC_WEB_PUSH_VAPID_PUBLIC_KEY=your-vapid-public-key
```

Only `EXPO_PUBLIC_*` values are bundled into the Expo app.

Generate Web Push VAPID keys once for the app:

```sh
npx web-push generate-vapid-keys
```

Use the public key in the Expo app env and store both keys as Supabase Edge
Function secrets. On iOS and iPadOS, Web Push works only for the installed Home
Screen web app on iOS/iPadOS 16.4 or newer, and the permission prompt must be
started by a user tap.

## Public Domain And Invites

Use `https://play.sucker.games` as the public web domain for landing pages and invite
handoff links.

Invite links generated by the app use:

```text
https://play.sucker.games/invite/<INVITE_CODE>
```

The app also accepts:

- `https://play.sucker.games?invite=<INVITE_CODE>`
- `sucker://invite/<INVITE_CODE>`

For production mobile builds, configure universal/app links so
`https://play.sucker.games/invite/<INVITE_CODE>` opens the installed app. The web page
at that URL should also show install/open-app options for users who do not have
the app installed.

Supabase is still the backend. Use a static host such as Cloudflare Pages,
Vercel, or Netlify for the marketing/landing site. Supabase Edge Functions can
serve simple HTML handoff responses, but they are not a full static-site hosting
workflow.

## Current Multiplayer Slice

Implemented:

- Supabase client setup with persisted auth sessions.
- Email sign-in with code entry plus magic-link fallback.
- Profile update helper.
- Remote game list/get helpers.
- Realtime subscription helper for `games`.
- Push token registration helper and Edge Function push sending.
- PWA Web Push subscription registration and Edge Function Web Push sending.
- Profile search helper.
- Invite-code helpers.
- Head-to-head stat lookup helper.
- Server-authoritative Edge Function for:
  - creating a game
  - creating invite-code games
  - accepting invite codes
  - rolling dice
  - accepting local held dice when rolls/scores are submitted
  - scoring a category
  - scratching a category for a Sucker Token
  - Extra Roll
  - Mulligan
  - chance-based Sucker Punch landed/blocked outcomes
  - Rage Quit forfeits and the winner's single reply
  - writing turn/action/token audit rows
  - recording game results and head-to-head stats at game completion

Production universal/app links, native build workflows, staged updates, and the real-device QA checklist are now configured. See [release-quality.md](release-quality.md).

Game mutations include client request IDs. The Edge Function stores each request outcome in `game_action_requests`, allowing uncertain network requests to be retried without rolling, scoring, charging tokens, or notifying twice. Legacy store binaries without request IDs remain supported while newer binaries roll out.

For hosted deployment, apply `20260712180000_game_action_idempotency.sql` before deploying the matching `game-action` function. Then release the updated client. This order keeps both existing and new store binaries functional throughout deployment.

Rage Quit (`20261016130000_add_rage_quit.sql`) follows the same order: migration, then `game-action`, then the client. The migration adds the `rage_quit`/`rage_quit_reply` action types, the public `rage_quits` table that drives the 24-hour salt badge, and matchup columns that keep forfeits out of averages and rates. A forfeit is stored as an ordinary completed game (`status = 'complete'`, `phase = 'complete'`, `winner_id` = the player who stayed) plus an optional `state.rageQuit`. Older binaries ignore that field, so they still open the game and show it as over, but they pick the winner by score and can show a quitter who was ahead as the winner. Their lobby and history labels have the same limitation. New binaries always honor `state.rageQuit` and `winner_id`.

Finishing a card after a Rage Quit (`20261029130000_let_rage_quit_winners_finish.sql`) follows the same order. The migration adds `game_player_results.played_out_at` and lets the high score boards count a finished card. `game-action` then accepts `finish_card`, which sets `state.rageQuit.playOut = 'playing'` and gives the winner every turn while the game stays `status = 'complete'`, and it refuses a Rage Quit until the quitter has filled 3 boxes. On the winner's last box, or at the quit when the winner's card is already full, it upserts their result with `played_out_at`, raises their matchup high score, and awards their card's feats. Older binaries refuse nothing locally, so an early quit from one fails with the server's "Too soon" error. They also cannot play a card in progress: they show the board but treat the completed game as unplayable.

Unseen results (`20261018120000_keep_finished_games_until_seen.sql`) follow the same order. The migration adds `game_players.result_seen_at`, marks every game that already finished as seen, and adds two RPCs: `get_unseen_game_results` (the caller's finished games from the last 7 days they have not seen) and `mark_game_result_seen` (marks the caller's own row, only up to the `updated_at` version they were shown). `game-action` clears the quitter's mark when the winner sends a rage-quit insult, so it needs the column first. New clients keep a finished game in the games list until that player opens it. If the lookup fails, they fall back to listing finished games under Completed. Older binaries ignore the column and move finished games to Completed immediately, as before. They never mark results seen, so the 7-day window keeps a player who upgrades late from finding weeks of finished games back in their list.

## Multiplayer Validation

Fast local gate for ordinary changes:

```sh
npm run typecheck
npm run typecheck:edge
npm run test
npm run test:edge
```

Server-authoritative multiplayer gate:

```sh
npm run test:integration:supabase
```

Web UI multiplayer gate at the mobile viewport:

```sh
npm run test:e2e:web
```

Keep a small manual/staging pass for behavior that depends on native devices,
hosted Supabase, or production link infrastructure:

- Hosted Supabase deploy smoke: apply migrations, deploy `game-action`, create
  two staging users, create/accept an invite, play one turn each, and confirm
  `games`, `turns`, `turn_actions`, token events, and head-to-head stats update.
- Push notifications: verify foreground, background, and terminated app delivery
  on iOS and Android devices for turn handoff, landed Sucker Punch, blocked Sucker Punch, and
  game-over events.
- Native deep links: verify `sucker://invite/<INVITE_CODE>` and
  `https://play.sucker.games/invite/<INVITE_CODE>` open the app and prefill/join the
  invite from a cold start.
- Background/foreground recovery: leave a game mid-turn, resume from the app
  switcher and from a notification, and confirm realtime state catches up without
  duplicating actions.
- Store-build smoke: run one invite game on TestFlight/internal Android builds
  against staging Supabase before promoting a release.

## Email Code Sign-In

The app is wired for Supabase email OTP codes with `verifyOtp`. To make hosted
emails show a code instead of the stock magic-link copy:

1. Configure a custom SMTP provider in Supabase Auth.
2. Open Supabase Dashboard -> Authentication -> Emails -> Magic Link.
3. Set the subject to `Your Sucker! sign-in code`.
4. Paste the contents of `supabase/templates/sign-in-code.html`.
5. Repeat steps 3-4 for the Confirm signup template. A new player's first code
   arrives through that template.
6. Enable Authentication -> Sign In / Providers -> Email -> Confirm email.

Confirm email is required. Without it, anyone can call the public `signUp`
endpoint with another person's address and a password, and that password keeps
working after the real owner later signs in with a code. With it enabled, the
`on_auth_user_email_confirmed` trigger also discards a password chosen before
the owner confirmed the address. Verify the hosted setting with
`curl "$SUPABASE_URL/auth/v1/settings" -H "apikey: $SUPABASE_ANON_KEY"`;
`mailer_autoconfirm` must be `false`. Local development keeps it disabled for
test-player logins.

The important template variable is:

```html
{{ .Token }}
```

Include `{{ .Token }}` so installed PWA users can enter a code in the app.
Keep `{{ .ConfirmationURL }}` as a secondary option for users who can open links.

Hosted redirect allow-list values should include:

- `https://play.sucker.games/auth/callback` for production PKCE sign-in
- `sucker://auth/callback` for development builds only
- `https://play.sucker.games/auth/callback`
- local Expo/web development URLs as needed
